## Role
The only coordinator: opens one HTTP stream per hop (microphone -> STT -> ai-agent decision -> TTS -> speaker), asks ai-agent for ONE decision per utterance, and is the only caller of the stepper. No hardware of its own. [C: `CLAUDE.md`, `application/services/`]

Nothing imports `pytest`, `pytest_asyncio` or `debugpy`. [C: a search of `application/ domain/ infrastructure/ composition_root/ main.py`]

## Hardware
None. Pure Python, `py3-none-any` wheels only [U: never run on arm64 or in Docker].

## Local
Works. `python main.py` on Windows: builds the adapters, runs the **startup preflight** (`GET /health` then `GET /available` of microphone, STT, TTS and speaker, every 2 s, 60 s), tries one ai-agent session (best effort), starts the voice pipeline in the background and serves. Brain's own suite gives **482 passed, 14 skipped** (the 14 are the live tests; `CLAUDE.md` still says 360) [D, 2026-11-10].

## Docker
No Brain-specific file. The deploy tool builds the generic image (`deployment/docker/service.Dockerfile`, `python main.py`) and runs `docker run -d --restart unless-stopped` (`docker_runtime.py:65`), so a Brain that exits after a failed preflight **is restarted by Docker already** [C]; never run [U]. The container reaches the other services through `host.docker.internal` (`topology.service_url`) [C].

## Configuration
Every setting comes from an environment variable, documented in `.env.example` and the table of `README.md` section 7. Loaded from `composition_root/setup/setup.py` (`find_dotenv(".env")`, **not** from `main_flow/http.py` as in the other services), and only when no VS Code launch profile was selected. The profile lookup reads `Path(__file__).resolve().parents[2] / ".vscode" / "launch.json"`, which is the **service folder** (`brain_microservice/`), not the workspace root as the first audit says: **Correction 2026-11-10: `.vscode/launch.json` is tracked in git, so a deployed clone has it too** (an image has it only if the build context keeps it). There the first profile is applied: `.env` is read through the profile's `envFile`, but the profile's `APP_ENV=development` overrides the `APP_ENV` of the `.env`; with `APP_ENV=production` in the process environment the `production` profile is chosen, its `envFile` is `.env.production` (absent) and `.env` is not read at all (decision Q02, fixed 2026-11-11). [C, D: a scratch copy without `.vscode` ran with `launch_profile: null`; with it, `launch_profile` was the first profile]

## Problems
Each one checked on 2026-11-10; the first audit's wording is kept where it was right.

1. **Silent localhost fallback. Confirmed [C, D].** `config.py` defaults every `*_BASE_URL` to `http://127.0.0.1:<port>` (microphone 8000, STT 8001, TTS 8002, speaker 8003, ai-agent 7998, stepper 8005). Run from a scratch copy with **no** `*_BASE_URL` at all, Brain started, logged nothing about it and `/integrations/health` said `All connection attempts failed` for all four, i.e. it was looking at its own machine. The audit's remedy "fail fast when unset in a non-development `APP_ENV`" **would never fire on a deployed robot**: the deploy tool does not set `APP_ENV` (`grep` of `deployment/`: only the settings inventory names it) and the code default is `development`. The deploy tool does always compute all six URLs when the layout places every service (a test requires that), so the risk is a hand-made `.env` or a native run. [C]
2. **Dev tools in the runtime requirements, unpinned. Confirmed [C].** `pytest`, `pytest-asyncio`, `debugpy`, and every package a lower bound. The deploy tool installs this file, so a Docker image of Brain carries the test tools.
3. **Brain exits when the preflight fails. Confirmed [D].** Microphone, STT, TTS and speaker unreachable with a 3 s timeout: the process ended with **exit code 1 after 6.7 s** and a `StartupPreflightError` traceback (60 s by default). Nothing restarts a native Brain; Docker does (`unless-stopped`). `wait_for_remotes` (the tool) only waits for services **on other machines** and only before a start (`deployment_service.py:132`); on one machine the tool starts the services in order and waits for each one's readiness. The preflight needs `is_available` of the four services and ignores a `reason` when they are available (see 7). ai-agent and stepper are not in it. [C]
4. **Shutdown stops the microphone over HTTP, so order matters. Confirmed [C]; the time is [U].** After uvicorn returns, `_cleanup` cancels the background tasks, calls `microphone_adapter.stop_stream()` (an HTTP POST with `PROVIDER_TIMEOUT_SECONDS` = 30 s), then `end_agent_sessions()` (one more HTTP call per flow, same timeout) and closes the clients. With the microphone stopped first and a refused connection the failure is immediate; a peer that hangs holds Brain for up to 30 s per call, far over Docker's 10 s `docker stop` grace, after which the container is killed (exit 137). A failure of the microphone stop is logged and swallowed. [C]
5. **uvicorn without `timeout_graceful_shutdown`. Confirmed [C].** `setup.py` builds `uvicorn.Config(app, host, port, log_config=None, timeout_keep_alive=60)`. The other services found on 2026-11-10 that an open request (a stream) makes `docker stop` wait until Docker kills the container (speaker: 10.49 s and exit 137; fixed with `timeout_graceful_shutdown=5`). Brain's inbound side has few long requests (`POST /voice/pipeline`, `/voice/transcribe`), but the same applies. [C], [U] for Docker.
6. **`Path(__file__).parents[2]` "workspace root". Corrected [C].** It is the service folder, **Correction 2026-11-10: the launch profile lookup is NOT harmless in a deployment**: `.vscode/launch.json` is tracked, so it overrides `APP_ENV` from the `.env` with `development` (the deployment manual says so, section on Brain's `APP_ENV`) and defeats any check that reads `APP_ENV` from the `.env`. Fixed 2026-11-11 (Q02(b), see the Update at the end).
7. **A simulated or fallback service is invisible to Brain. New [C].** `HttpServiceClient.check_health` answers `healthy and available` whenever `is_available` is true and **drops the `reason`**; microphone `sim`, speaker `null` and TTS `pyttsx3` fallback all say so in the `reason` of `/available` and the deploy tool prints it as a warning. Brain's preflight and `/integrations/health` show nothing: a robot whose speaker is `null` starts, passes the preflight and is silent. [C: `http_client.py`, `deployment/CLAUDE.md`]
8. **`STARTUP_PREFLIGHT_ENABLED`.** A switch (default `true`); false skips the wait and Brain starts with every service down (the pipeline then retries). Confirmed [D] in the same scratch run: `/health` 200 while the four services were down. [C, D]
9. **Echo guard and speech cues depend on timing, not on a device. Confirmed [C].** `EchoGuard` and `SpeechCues` are computed from the bytes Brain sends to the speaker (`tts_to_speaker.py`), not from what the speaker answers, so a `null` speaker does not change them (speaker Q01-3). A real-room acceptance (the microphone hears the speaker) needs the real devices: a manual task.
10. **Tracked bytecode. New [C].** 23 `__pycache__/*.pyc` files are tracked although `.gitignore` lists them; the deploy tool filters them from the Docker context. Noted, not part of this plan.

## Not a problem (checked)
- **Logging** is `shared_logging` only; `LOG_LEVEL` and friends are the shared package's. `APP_ENV` only fills the log field.
- **`python-dotenv`** is imported inside a `try`; a missing package would silently skip `.env`, which is another reason to keep it in the runtime file. [C]
- **ai-agent** is a dependency only: Brain's adapter calls its `/session/...` routes; nothing here edits ai-agent. In the workspace pipeline check 21 tests that drive Brain against a real ai-agent process fail today because of ai-agent's work in progress (it bundles `contracts` 0.15.0). [D]

## Recommended changes
1. Split the requirements (runtime pinned with `==` to what ran, a `requirements-dev.txt` with `pytest`, `pytest-asyncio` and the lint tools; `debugpy` follows Q01-6).
2. Missing `*_BASE_URL`: decide fail fast or warn (Q01-1); either way tested and named in the log with the variable and the default it fell back to.
3. `timeout_graceful_shutdown=5` and a bounded cleanup (the microphone stop and the session end must not keep Brain alive past the Docker grace period).
4. Surface the `reason` of an available service in Brain's log and `/integrations/health` (Q01-3).
5. Keep the preflight exit and rely on Docker's `unless-stopped` for a native-free restart policy; prove it in Docker (Q01-2). No code unless the answer is "wait instead of exit".
6. Prove Brain on this PC without hardware (Q01-4) and the real voice round trip with the maintainer (manual).
